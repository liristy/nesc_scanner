# 电池报警自动核查需求汇总

整理日期：2026年9月27日  
适用平台：[超电云平台](https://cloud.cnano.com.cn/)  
程序目录：`D:\CnanoBatteryAudit`

本文汇总历次对话中提出的要求，以最后确认的口径为准。已经被替代的要求列在文末，不与现行规则并行执行。程序采用的具体阈值和技术方案另列说明，避免将实现细节误写成用户最初逐项指定的要求。本文是需求归档，不是当日核查结果，也不代表对当前运行状态的重新验收。

## 一、目标和使用方式

自动核查电池报警，识别需要通知客户补电的对象，汇总各类报警，并发现同一型号是否集中出现相同问题。

- 每个中国法定工作日自动运行，考虑节假日和调休。
- 封装为Windows可自动执行的脚本，不依赖每天打开Codex、打开平台网页或手动点击开始。
- 尽量自动登录、自动重试和续查，减少人工操作。
- 日报要简洁、及时、容易找到，能够直接转发老板；工程师另看完整复核清单。
- 自动处理限于平台读取、分析和本地报告。客户补电通知由人工落实，程序不自动向客户发送消息。

## 二、核查对象与报警筛选

### 2.1 第一前提：厂商必须为JY

- 必须先筛选平台实际的“厂商”字段为`JY`，再核查和统计；当前报警页面对应显示为“BMS厂商”。
- 其他厂商不核查、不统计，不进入关注名单或客户补电提醒名单。
- 不以拥有者、站点、SN或BMS编号前缀替代厂商字段判断。
- JY规则用于后续核查，不因此追溯修改已交付的2026年9月16日报告。

### 2.2 只统计未恢复的保护报警

- 报警级别只选“保护”，不选“提示”。
- 重点是“修复时间”字段为空的记录。
- 以下三个报警项忽略，不计入统计和跟踪名单：

| 忽略项 |
| --- |
| 物联网模块已解绑 |
| 物联网卡号变更 |
| BMS编号异常 |

- 其余符合条件的保护报警均须分类汇总，不只关注电量不足和单体压差过大。
- 核查中发现之前的报警已经恢复，可以剔除。固定截止时间不妨碍更新原有记录的恢复状态。
- 恢复复查只剔除已经恢复的对象，不把截止后新增的报警扩大纳入本轮。
- 当前统计按同一电池、同一报警类型保留截止范围内最新一条未恢复记录；应注明去重口径，区分报警条数与电池块数。

## 三、单体压差过大：排除异常读数并单列复核

点开电池详情，在“基本信息”中读取真实BMS编号，并查看“电芯信息”。

| 基本信息BMS前缀 | 电池体系 | 合理电芯电压范围 |
| --- | --- | --- |
| F1 | 三元锂 | 2.7—4.2V，含边界 |
| F3 | 磷酸铁锂 | 2.6—3.6V，含边界 |

- 任意一节或多节电芯低于下限或高于上限，按用户约定归入平台／模块读数问题，将对应的“单体压差过大”报警从正式统计中剔除。
- 被剔除的压差报警必须集中单列，保留具体对象及读数，供后续复核，不能直接丢弃。
- 仅剔除该条压差报警；同一电池的其他保护报警仍按各自规则判断和统计。
- BMS类型不明、字段缺失或电压证据不足时，不猜测、不判正常，标注待复核。
- 此处是用户指定的统计处理规则，不表示已经通过现场检测证实具体故障原因。

## 四、电量不足、低压保电与客户补电名单

### 4.1 以心跳记录为依据

- 平台SOC不够准确，不能只凭SOC判断是否需要补电。
- 必须关注心跳记录中的最低电芯电压及“进入低功耗”事件。
- 最低电压低于2.8V，且有“进入低功耗”记录，归入低压保电观察对象。
- 进入低功耗后仍可能继续上报电量不足，不能因为进入低功耗就删除这类报警。

### 4.2 急需补电风险条件

用户提出的核心条件是：欠压、最低电芯电压低于2.5V，且心跳记录中的电量不足报警持续长达一周；符合条件的对象需要提醒客户及时补电。

- 结合低功耗记录和历史心跳证据复核，不把单次低电压直接写成“持续一周”。
- 明确区分“已确认满足补电风险条件”和“低压、但历史证据不足的优先复核对象”。
- 证据不足不能视为正常，也不能冒充已确认的急需补电名单。
- “低于”采用严格比较：2.50V不算低于2.5V，2.80V不算低于2.8V。
- 已确认需要补电的对象，在老板日报中必须列出**基本信息中的真实BMS编号**；不能用电池组SN替代。
- 名单同时给出客户、最新有效最低电芯电压、持续时间或证据跨度，以及待通知状态。程序未发送通知时不得写“已通知”。

### 4.3 当前程序对“一周”的保守证据细则

以下是为落实上述要求采用的自动判定细则，不是用户最初逐项指定的全部数值：

1. 有效的保护级电量不足记录跨度至少168小时。
2. 相邻保护报警记录间隔不超过24小时，末条报警距统计截止时间不超过24小时。
3. 在该段记录中未见有效最低电压回升至2.8V或以上。
4. 最新有效最低电芯电压仍低于2.5V。
5. 该段记录中有“进入低功耗”事件。

当前程序对低于2.5V的对象继续读取近9天历史，支撑一周判断。平台标记为“异常数据”的心跳不作有效电压证据；数据缺失或历史不够长时注明缺口。记录跨度不等于连续实时测量，也不等于现场实测。

## 五、执行时间与统计区间

| 项目 | 现行要求 |
| --- | --- |
| 时间基准 | 北京时间，与平台16:00口径一致 |
| 执行日期 | 中国法定工作日，包含调休补班日 |
| 报警截止时间 | 当天16:00 |
| 开始分析时间 | 截止后即开始，即16:00，不再等到16:30 |
| 区间起点 | 上一次成功核查的截止时间 |
| 区间边界 | 上次成功截止时间不含，本次16:00含 |
| 报告完成时间 | 实际分析完成后出报，16:00不是保证出报完成的时间 |

- 周一应覆盖上次成功截止后的周五下午、周六、周日及周一截至16:00的数据。
- 长假、调休和失败后的补查，均按照连续区间衔接，避免漏查。
- 法定休息日不按普通工作日执行；调休补班日即使是周末也执行。
- 失败或未完整核查，不推进“上次成功截止时间”；后续自动续查或补查。
- 本次新增记录与前次延续的未恢复问题分别标明，不能将历史延续量全部称为“今日新增”。
- 固定的是报警纳入范围。核查时读取的详情电芯信息或恢复状态可能晚于16:00，须保留采集／复查时间，不伪称16:00现场快照。

## 六、滚动跟踪和空间控制

核心要求：**每次跟踪“前次仍有问题的电池＋本次新增报警电池”，避免每日积累大量正常对象的心跳JSON。**

- 成功生成报告后，将仍需跟踪对象的原始证据集中放入`D:\CnanoBatteryAudit\跟踪数据`。
- 每块待跟踪电池只保留最新一份资料，下次成功核查后替换旧副本。
- 已恢复且没有其他待复核问题的电池，不再保留其原始心跳和重复跟踪数据；以后出现新报警时重新纳入。
- 未恢复保护报警、被排除但仍待复核的压差报警、低压风险和证据不足对象，都不能误当作正常对象删除。
- 清理应在报告和跟踪资料成功保存后进行，不能先删证据再分析。
- 失败、未完成区间所需的原始资料、续查进度及登录资料不清理。
- 每日简报和工程复核清单继续保留，包括Markdown和HTML版。
- 型号趋势只保留少量滚动汇总计数，不为趋势分析额外长期保存每条心跳。

## 七、日报形式与内容

### 7.1 固定双文件交付

| 文件 | 阅读对象 | 内容定位 |
| --- | --- | --- |
| `今日电池报警简报.md` | 老板、日常转发 | 简洁结论和需要采取的行动 |
| `电池报警复核清单.md` | 工程师 | 对象明细、证据及排查依据 |

同时生成对应HTML，方便打开查看。保留双文件结构，不合并成一份难读的长表。

### 7.2 老板版采用“版本一·消息速报”

用户在2026年9月22日明确选择版本一。按以下顺序编排：

1. **客户补电名单**：先写已确认数量；有对象时逐项列BMS编号、客户、电压、证据跨度、待通知状态。低压但未确认的对象用数量和待复核说明表达。
2. **报警数量**：共多少种、多少条、涉及多少块；每一种报警各多少条；区分本区间新增和历史延续。不能把多个类型全部藏在“其他报警”中而不给明细数量。
3. **同型号集中异常**：是否有某个型号集中出现同一种问题、涉及多少块、与历史相比是否增加；数据不足就明确注明。
4. **工程重点**：简要提示短路、高温等需要优先核实的问题及处理方向。

除了急需补电对象，老板版不堆具体SN、长心跳索引和逐条工程证据。正文要能直接用于每日向老板汇报。

### 7.3 工程复核清单

保留以下详细内容：

- 具体电池对象、平台详情链接、所属客户／站点。
- 真实BMS编号、平台型号及电池组编号之间的对应关系。
- 已确认低压风险、未确认的一周风险、其他低压保电观察对象。
- 最低及最新有效最低电压、低功耗事件、历史覆盖范围和证据缺口。
- 压差越界排除项，以及保留或资料不足的压差报警。
- 全部保留的报警及其类型、时间、新增／延续分类。
- 心跳核查索引、异常数据情况、已恢复剔除情况。
- 同型号集中问题的完整分组、数量和比较依据。

### 7.4 报告可访问性与表达

- 报告不能运行完就“消失”，必须有固定位置和桌面入口。
- 在聊天交付日报时，先给简要重点，再给简报和复核清单两个直接文件链接，不只说“在报告文件夹里”。
- 有哪些缺口就写哪些缺口，不把“尚未证实”说成“没有风险”。
- 报警记录数不等于已确认实体故障数。

## 八、同型号集中问题分析

### 8.1 用户明确要求

- 关注是否有某个型号突然出现一模一样的问题。
- 老板主要看型号、问题类型、数量和变化，不需要逐条SN。
- 用户于2026年9月22日授权补上该功能，要求从次日自动核查起可用。
- 型号取平台基本信息的真实“型号”字段，不通过SN或BMS前缀猜测。
- 不能因同一批旧报警一直未恢复，就把它写成今天集中爆发。

### 8.2 当前程序采用的默认判定细则

这些阈值是实现方案，不是用户最初直接给出的业务数值；调整时应保持口径透明。

- 只比较本区间新增、复查仍未恢复且已按规则排除异常压差的保护报警。
- 按“型号＋报警类型＋截至16:00的逐日窗口”分组，同一组按独立电池去重。
- 周末和长假拆成逐日窗口，不把多日总量与单日日均直接比较。
- 历史基线取此前30天内最近7个完整、型号齐全的统计日；至少取得3个有效历史日，才进行突增判断。
- 同类单日新增至少3块，达到历史日均的3倍，且比日均至少多3块，提示“疑似突增”。
- 历史日均为0而当日达到集中阈值，提示“新增集中出现”。
- 历史不足、统计覆盖不全或型号缺失时，只列已观察到的集中分布及缺口，不直接认定突增、型号故障或故障率上升。
- 老板版最多列3组重点，完整分组放工程清单。
- 聚合历史滚动保留35日，保存型号、报警类型和计数，不保存额外SN或原始心跳。

## 九、后台运行、登录和失败处理

### 9.1 无需手动打开网站

- 日常运行不要求用户提前打开平台网页或登录窗口。
- 可以在后台完成读取分析；显示进度窗口不代表需要用户操作网页。
- 当前采用后台浏览器读取已登录平台的方式。用户要求的是无人值守执行，并未要求必须改用某个HTTP接口或特定爬虫技术。

### 9.2 自动登录

- 不要每次要求手动输入账号密码。
- 首次配置或修改账号密码时，通过Windows本机安全输入框录入。
- 凭据和会话只在本机、当前Windows账户下加密保存到D盘`private`目录；不输出到聊天、日志、命令行或安装包。
- 会话失效时自动重新登录。
- 凭据被拒绝或平台要求额外验证时，停止重复登录并提示人工处理。
- 首次凭据验证不得抢占正在运行的核查会话。

### 9.3 失败自动续查

- 网络、超时、分页等普通故障应自动重试，不要等用户手动点“重新分析”。
- 当前普通重试等待60秒、180秒，总共最多3次，沿用同一统计截止和可复用的检查进度。
- 不同时重复启动多轮核查，不因重试改变统计截止时间。
- 重试耗尽或确需人工处理时，清楚提示原因及入口；不能把失败显示为成功完成。
- 成功截止时间只在必要读取、恢复复查和报告保存均完成后推进。
- 运行前提：电脑开机、联网，安装任务的Windows账户保持登录；锁屏可以，关机或注销无法现场执行。错过执行时应在可运行后补查。

## 十、实时进度、系统通知和固定入口

### 10.1 运行期间能看见进度

- 每天定时运行也应自动显示检查到哪里，例如“已检查数量／总数”，不能只弹一个空白窗口。
- 手动补查和定时启动都要具备进度显示，不能只修手动入口。
- 独立进度窗口只读日志；关闭该窗口不停止后台核查。
- 后台核查结束后，自动打开的进度窗口自动关闭。
- 用户可以通过桌面“JY核查实时进度”或`08-查看实时进度.cmd`再次查看进度。

### 10.2 完成或失败使用Windows原生通知

- 不使用用户不喜欢的自制置顶弹窗。
- 完成后在系统通知中展示简要日报状态，并提供简报、复核清单入口。
- 最终失败时提示失败状态和运行状态入口。
- 保留桌面“JY电池日报”入口，通知收起后也能找回报告。
- 系统通知与实时进度窗口是两个用途：前者告知结果，后者显示运行过程。
