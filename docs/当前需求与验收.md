## 重构验证及回退

`heartbeatTransport=source`使用当前已登录浏览器会话的只读心跳查询，历史日复用已核对设备的查询模板，原始模板不落盘。每个SN原子保存检查点，失败设备最多按配置并发补查。只对压差对象请求实时电芯。2026-10-13简化后，仅进入完整采集队列的对象读取基本信息及必要心跳；历史仅恢复复查对象复用原资料，不重读设备证据。

`heartbeatTransport=rendered`保留旧页面表格读取，用于现场对照和回退。必须在真实平台小批次验证后评估端到端提速；本地模拟请求数与时间不能冒充生产结果。

2026-10-11现行策略：`auditPolicy=current_day_pending`，云端配置及本地默认均采用该值；`continuous`仅保留为旧规则回归/显式回退。下面2026-10-05关于缺失设备补查、旧截止续查和批次失败阻止整轮完成的描述属于已被替代的历史实现；证据完整性、身份验证、保存顺序仍继续适用。

用户主要入口：Actions本次运行首页Summary中的“实时进度入口”，点击“打开GitHub实时进度”。短入口任务先完成，采集运行中即可显示链接。GitHub原生检查页每15秒收到最新计数，刷新可见，无需本地服务、另建长期令牌或公开发布设备数据。使用工作流临时令牌的checks写权限；进度API故障不影响采集。日志仍持续显示进度，工作流最终收尾后才标记原生进度检查完成。

2026-10-05补充：报警恢复复查以查询批次独立计数，查询中显示当前批次的原报警日期及目标SN。已处理包含失败批次，通过与失败分开显示；限额未查询、取消及会话失效保留未完整/中断状态，不把设备采集100%或批次处理100%当作最终成功。复查进度不改变原报警身份校验、保存和截止推进规则。

2026-10-05续查优化：设备必要证据缺失且尚有重试次数时，先保存逐SN原始检查点，暂缓全量最终报警恢复复查，按原三次总预算及60/180秒等待补查缺失设备。每轮仍刷新历史候选；设备证据补齐或到最后可用轮才执行最终复查，并按当时的原始报警身份、恢复状态和历史风险重新判定。最终复查失败仍须重新查询，不缓存为成功。明确离线只豁免实时电芯，其他证据缺口及保存失败不推进截止。进度显示等待补证据的块数。

本地 `npm run progress` 网页只作为本地运行工具，不是GitHub工作流中的页面。服务器只触发任务，采集进度来自Actions，不来自服务器timer。

2026-10-04故障优化：原始心跳按SN原子保存，运行与续查只在内存保留摘要、按需读取单块证据；新证据包不重复打包整轮和批次心跳，失败历史日期仍保留。默认单日上限提高至60000条，每页仍最多300条，完整性规则不变。当天分页增长只有在记录按时间倒序、旧记录内容一致、旧总数完整读齐，且重新核对第一页证实新增前缀全部晚于固定截止时才接受；总数下降、截止内新增或无法证明覆盖仍须重试并保留缺口。低压报警链分析改为线性扫描，168小时、24小时间隔、回升及低功耗规则不变。复查、保存和重试准备阶段清空设备读取阶段的剩余时间预估。
